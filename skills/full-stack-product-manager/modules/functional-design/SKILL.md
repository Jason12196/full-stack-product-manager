# 功能方案

继承主 skill 的确认与每次修 bug 的流程。先以证据核实当前实现，再提出最小改动，不能先写补丁再解释方案。

## 核实当前实现

1. 从功能入口追踪调用链、输入转换、服务边界、持久化与输出；读取适用项目规则和已有未提交改动。
2. 定位正常的类似实现、共享工具、状态/权限/错误模型。区分当前已有能力、需要调整能力与确需新增能力。
3. 诊断 bug 时记录复现步骤、预期/实际结果、首次失败边界、错误信息和最近相关变化。根因不明时给调查方案，不伪装成已确定修复。
4. 请求参数、环境传播和组件边界需分别验证；一层成功不能证明下一层成功。诊断日志不泄露密钥、个人信息或完整敏感请求。

## 最小方案内容

- 目标与功能 ID，关联竞品及交互约束。
- 当前实现的准确路径/符号/调用关系、证据与未验证假设。
- 推荐方案、必要权衡；仅在确有选择时比较替代方案。
- 修改清单：文件与函数/组件、修改原因、新增/调整/删除、复用对象。行号是当前快照定位，不是永久标识。
- 冗余检查：已有工具/逻辑/样式是否承担相同职责；不要默认创建新抽象。
- 冲突检查：适用的类型与接口、状态、权限、依赖版本、配置、迁移、并发、缓存和未提交工作。
- 带颜色与文字标签的功能流程图，反映真实处理顺序与失败节点。
- 错误矩阵、回退策略、验收与适当验证，明确确认点。

## 逐节点错误分析

按实际流程判断适用项，不无条件实现全部机制：

| 类别 | 应检查的问题 |
|---|---|
| 输入与权限 | 缺失、格式、边界值、权限不足、认证失效 |
| 网络与依赖 | 不可达、超时、取消、限流、上游无效响应 |
| 状态与并发 | 重复请求、幂等、竞态、过期状态、重复提交 |
| 数据与持久化 | 不存在、冲突、部分成功、事务失败、迁移兼容 |
| 资源与任务 | 配额、文件限制、任务中断、残留资源 |
| 用户恢复 | 可重试条件、次数/停止条件、已完成工作保留 |

对每个合理失败点列：触发条件 → 检测位置 → 内部错误类别/已有错误码 → 用户提示 → 诊断信息 → 重试/回退/终止 → 验证场景。保持已有错误规范；新增错误码只在确有必要时采用。

不吞错、不用空结果冒充成功、不无限重试、不用通用 catch 抹平可区分原因。原始技术信息用于合适的诊断渠道，用户提示应能解释发生了什么以及可以做什么。

## 交互路径与诊断契约

从实际交互入口梳理提交、等待、成功、失败和适用的取消、重试、恢复路径，追踪到服务与持久化边界；纯后端任务从调用方入口梳理。每条合理失败路径都必须有检测、分类、诊断记录与返回契约，不能因为不向用户展示技术细节而省略报错机制。

优先复用后台统一错误处理与诊断设施：后台保留错误码、失败节点、原因/异常链和必要的脱敏上下文，以请求/任务关联标识串联调用链；不向前端返回堆栈、密钥或敏感原始数据。前端按稳定错误码映射对应提示与恢复操作，必要时只附可用于定位的关联标识。方案明确错误码归属、映射维护位置、未知错误码的安全提示及诊断检索方式，避免各层重复记录同一异常或各自建立错误码体系。仅前端可检测的失败沿用适当的本地诊断或已有上报机制，不强行依赖不可达的后台。

错误矩阵补充：交互路径 → 失败节点 → 错误码 → 后台诊断位置/字段 → 前端映射 → 恢复与验证。检查合理失败路径均可定位；明确未覆盖项，不声称穷尽所有异常。

## 回退与验证

区分业务回退/降级、部分操作补偿、代码发布回滚，不能把它们当成同一机制。明确触发、执行位置、已有数据/结果保留、兼容性和权限。不可逆变化要如实说明恢复限制；没有合理回退时直接报错并保留诊断，不虚构兜底。

验证覆盖目标行为及受影响的关键失败路径。选择已有测试、复现、构建或手动检查等适当方式；不写仅镜像实现的测试，不为了低风险变更扩张测试范围。

## bug 修复的必经流程

只读复现 → 定位根因或列出调查假设 → 修复方案 vN（具体代码、图、错误与回退、验证）→ 用户确认 → 实现 → 验证。

新增诊断代码也要先确认；同一问题验证失败后先分析原因，修改修复方向必须再确认。实现中发现的 bug 不能例外。若修复不再符合原批准方案，立即停止写入并提交修订版本。

## 可维护性与方案基线

读取现有实现时检查当前分支/上游；每轮实际代码写入前仍须重新执行主 skill 的同步检查。上游有更新时安全同步、review 一轮，再校正方案中的文件、调用链与复用判断。

方案明确模块职责、依赖方向、状态所有权、接口契约及错误模型；沿用项目已验证的风格与设计模式，优先简单局部变更。检查重复逻辑、过深分支、隐式副作用、跨层耦合、无依据的新依赖与过度抽象。说明未来扩展点和下一次同类修改位置；偏离现有模式须给收益、代价及确认范围。不把维护性 review 中发现的问题直接当成重构授权。

技术方案阶段就落实代码设计的工整度与后续维护点：命名、格式、职责和控制流清晰，指出错误码/提示映射、接口和状态下一次应在哪里维护。新增逻辑逐项核对已有实现，避免重复分支、重复转换、重复错误处理和无实际用途的封装；实现阶段仍必须重新审查最终代码，不能以方案已评审代替实现后的维护性与冗余检查。
