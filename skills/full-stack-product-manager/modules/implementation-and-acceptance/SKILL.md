# 实现与验收

继承主 skill 的全部规则。负责最终集成质量，不自行扩展需求或把发现问题当作修复授权。

## 开始前的门禁

核对功能 ID、方案版本、明确批准记录、具体范围和回退条件。检查交互与功能方案中的状态、接口、错误表现是否一致；只做后端任务不强制创建交互方案。隔离展示与正式集成分别核实授权。

检查工作区与项目规则，保留无关修改。将批准范围拆成可验证步骤，不为了流程创建无用文档。开始一批代码写入即记录轮次，验证后新修改计下一轮；不能用长批次掩盖反复试错。

## 实施把关

- 优先复用已有组件、工具、样式和错误机制。
- 检查调用顺序、数据/状态流、资源生命周期、权限以及适用并发边界。
- 对照方案逐条走通交互与调用路径，落实失败检测、错误分类、诊断记录和错误返回；技术细节不展示给用户也必须可诊断。优先后台统一处理并记录脱敏原因与关联标识，前端按稳定错误码映射提示和恢复动作；沿用已有机制，不复制错误体系或重复记同一异常。
- 避免复制工具函数、相同组件和重复样式；按实际职责提取，不能为去重制造更复杂的抽象。
- 保持隔离展示的路由、数据、依赖和样式边界，明示模拟能力。
- 删除冗余或重构须在批准范围内；范围外发现记录为遗留或新提案。
- 新关键约束、新根因或范围变化时暂停，更新方案再确认。

## 验收

建立功能 ID → 验收场景 → 检查方式 → 实际结果/证据的对应。按适用范围检查：

1. 正常行为满足需求，并与对应竞品的采用范围一致。
2. 交互可点击，状态反馈、键盘与焦点、适用布局正确。
3. 对照错误矩阵检查关键失败路径：后台能通过错误码与关联标识定位失败节点及脱敏原因，前端能映射对应提示/恢复动作，未知错误码有安全提示；技术细节不泄露，模拟与真实结果不混淆。
4. 回退/恢复/重试有终止条件，已有结果和数据按方案保留。
5. 相关构建、类型、测试或集成检查通过，没有用静态检查替代实际行为。
6. 检查最终 diff 中是否有范围外改动、重复代码/样式或未清理展示痕迹。

检查通过后不无意义重复扩大测试；失败检查、缺失环境和未验证路径必须写明。

## 执行后对齐用户实际感知

每次实施或修复完成后，从用户实际使用的入口、角色与场景走一遍关键链路，核对需求和已批准方案在用户眼中的结果。检查对象是最终集成的功能；隔离展示通过不能证明主产品表现一致。纯后端功能也要追到实际调用方能够观察的结果。

- **结果感知**：用户能否看到、找到并使用预期结果；数据保存、刷新和再次进入后的表现是否符合需求。
- **过程感知**：点击是否有反馈，等待、进度、禁用与重复操作是否清楚，完成状态是否准确。
- **失败感知**：用户能否理解失败原因、知道下一步，并完成适用的重试、恢复或回退；保留的数据与结果是否可见。
- **体验对照**：对照采用的竞品功能和已确认交互，记录实际一致项与偏差，不用接口成功或截图外观代替完整行为。

交付时分别报告“技术验证”和“用户感知验证”，给出操作步骤及实际证据。Agent 的体验核对不等于用户本人认可；用户尚未反馈时不要声称用户已验收。缺少浏览器、权限、环境或真实数据时，明确哪些感知路径未验证，并给用户最小复核步骤；不能默认通过。

若技术检查通过但用户反馈“没变化”“找不到”“仍然报错”，将反馈作为待核实证据，重新检查实际入口、版本与环境、权限、缓存和完整调用链。先诊断，再按修复方案确认流程处理；不能仅重复技术检查结果或直接追加补丁。纯文档/skill 任务则核对安装、发现、阅读和调用入口是否可理解、可使用，并说明尚未实测的行为。

## 发现 bug

立即记录独立问题 ID、复现、影响与证据。读取功能方案模块，提交修复方案和图，等确认后修。即使 bug 是刚才实现造成的也不得省略；可以继续与它无关、已批准且安全的步骤，不能跨过阻塞条件假装完成。

批准的回退条件满足时执行已授权回退并计轮次；没有回退授权就提交回退方案。不要默认自动重置工作区。

## 遗留与交付

每个遗留问题保留 ID、影响、原因/证据、状态和建议下一步。已修复问题用验证证据关闭；延期或接受限制标明用户决定，不静默删除。

最终回复报告实现内容、适当验证及其边界、遗留问题、入口/文件链接和状态栏。发布、commit、push、生产操作仅在已有明确授权时执行；本模块不提供额外权限。

## 每轮写入前同步，完成后维护性 review

首次及后续每轮代码写入前执行主 skill 的当前分支检查。有上游更新则按安全策略同步，并 review 一轮新引入提交；没有更新也要记录检查结果。分叉、脏工作区、无上游或 fetch 失败按主规则处理，不自动 stash/reset/rebase，也不在旧方案失效后继续写入。

每批实现完成后 review 最终 diff：命名/格式符合项目风格，模块与组件职责明确，依赖方向及状态所有权一致，接口/错误模式可读可验证；检查重复代码/样式、隐式副作用、过度抽象与无关变更。结合后续同类变更确认扩展位置，记录维护性结论与具体问题。上游更新 review 与本次实现 review 是两个独立检查，不能互相替代。发现待修问题进入诊断、方案、确认流程，不顺手改。

实现完成后必须重新检查代码工整度、可维护性和冗余，不能只引用方案结论。对照改动清单与已有实现，核对命名/格式、控制流、职责、复用及后续修改位置；确认未新增重复逻辑、无用封装、重复错误映射或重复诊断。交付时记录实际检查范围、结论、证据及未解决项；本次新增冗余未处理时不得宣称通过验收。整改遵守既有批准范围与修复流程。
