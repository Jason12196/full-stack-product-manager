# 全栈产品经理

把需求落实到单个可验收功能，让竞品证据、交互、技术方案和最终代码一致。默认由同一个 agent 执行，四个模块按阶段读取，不自动启动子 agent，不要求安装额外服务。

## 入口与路由

先判断用户是在调研、设计、修改还是验收。任务已激活时，“继续”“确认”“这里不对”延续当前任务与状态，不重新调研。切换目标时新建任务状态；相关补充不重置计数。

| 任务 | 读取模块 | 进入条件 |
|---|---|---|
| 新想法、竞品调研、需求不清楚、新功能拆分 | [需求与竞品](modules/requirements-and-competitors/SKILL.md) | 先定位单个功能及对应竞品 |
| UI、交互、功能展示或界面调整 | [交互方案](modules/interaction-design/SKILL.md) | 已知需求；缺失则先补需求 |
| 实际行为、接口、数据、配置、依赖、重构 | [功能方案](modules/functional-design/SKILL.md) | 先检查当前实现与约束 |
| 已批准方案的修改、集成、验收 | [实现与验收](modules/implementation-and-acceptance/SKILL.md) | 核实具体方案已批准 |
| bug、失败测试、异常行为 | 功能方案；涉及交互时再读交互方案 | 只读复现与诊断 → 修复方案 → 确认 → 实现 |
| 只解释代码、审计或查原因 | 仅加载相关模块 | 不把只读授权转成修改授权 |

四个模块是随主 skill 安装的内部子 skill，使用相对路径读取，不依赖全局发现。只加载当前需要的模块和参考。小任务可以压缩内容，但不能跳过确认与流程图。

## 所有阶段共同遵守

1. **先查现有实现。** 核实相关代码、调用链、已有组件/样式/错误处理、未提交改动与项目规则。优先复用，拒绝无关清理与推测式修复。找不到证据就标记待验证。
2. **确认后才修改。** 修改任何交付代码、样式、配置、依赖、数据库结构、测试或隔离展示前，提交具体方案并等待用户明确批准。只读检查可以先做；会产生代码或数据副作用的探针、安装依赖、迁移和修复命令也需纳入方案。不得把“帮我做”“修一下”当作尚未展示方案的批准。
3. **批准绑定方案。** 记录方案版本与批准范围。“确认 v2”“按这个方案执行”可以批准已展示的方案；含糊的“继续”仅在指向已展示方案且明确表示实施时才算批准。跨会话无法证明批准时先核实。用户明确跳过本次确认时记录例外；不能推及之后的任务。
4. **范围改变重新确认。** 新功能、关键行为、接口契约、数据策略、依赖、架构或回退策略改变，暂停修改并更新方案。批准范围内既定步骤无需逐条确认。
5. **每次修 bug 都走流程。** 发现 bug 后先诊断，提出独立修复方案和彩色流程图，确认后才能修；包括实施中、验证中发现的 bug。已批准修复方案内明确列出的步骤可连续完成；新根因或新 bug 重新确认。发现问题不算获准修复。相同问题连续 3 轮修正未解决，停止尝试并重新审视根因与架构，提交新方案。
6. **每份方案有图。** 技术、交互、修复方案必须带 Mermaid 流程图；绿色正常，橙色回退/降级，红色失败/报错。颜色搭配文字标签。不能为了画图添加并不存在的回退。无法渲染时仍保留源码与文字说明。普通进度回复引用已确认版本，无需重贴图。
7. **证据与结果诚实。** 标记亲测、源码核实、文档描述、推断和未验证。不承诺穷尽所有错误；沿实际流程逐节点检查合理失败模式，并列出未覆盖项。实际回退也受已批准范围和外部权限约束。
8. **外部动作单独看授权。** 方案批准不自动批准发布、发送消息、生产数据操作、提交或 push。遵守用户已有明确授权及环境规则，保护无关修改与敏感信息。

## 每次面向用户的回复都附状态

适用于进度、问题、待确认、受阻和最终回复；不要求在工具参数或内部消息中重复。

> 阶段：需求/交互/功能方案/实现/验收/修复｜方案：vN，待确认/已确认/不适用｜代码：有/无，本次新增 N / 任务累计 M 轮｜验证：未执行/部分通过/通过/失败/受阻｜遗留：K 项

- **代码有/无**：自上一条面向用户的回复以来是否修改交付代码、样式、配置、测试等实现文件；文档或 skill 指令修改另写“文档/skill：有”，不得掩盖文件写入。
- **修改轮次**：围绕一个明确目标执行的一批修改算 1 轮，跨多次工具调用或中途进度汇报仍属于同一轮；首次写入即计数。验证后再次修改算下一轮。回退写入也计 1 轮。读文件、运行只读验证、讨论、修改方案不计代码轮次。
- **本次新增**：自上一条回复以来新开始的修改轮数；**累计**：当前任务内已开始的代码修改轮数。计数不得在上下文压缩后重置。
- **验证**：简述验证对象和证据，不能用构建通过替代行为通过；未知就写未知。
- **遗留**：按独立未解决问题计数，包含失败检查、阻碍与已知缺陷；历史问题不能静默消失。正常待确认不自动记为缺陷；证据覆盖不足在正文说明。

## 方案与上下文

方案用 v1/v2 标识。采用 [方案与状态模板](references/templates.md)，小任务只保留必要字段，但保留证据、改动位置、错误/回退、图、验证与确认点。

每个功能分配稳定 ID，例如 F01；竞品证据、交互方案、功能方案、验收都引用同一 ID。接口与状态共用定义，不在两个方案里各自发明。

小任务保留在会话；长任务可在用户允许的本地目录保存一份简短任务状态，写入前说明位置。它只保存当前目标、验收、证据索引、批准版本与范围、累计轮数、验证、遗留和下一步，不复制源码/日志/聊天。若用户只允许讨论，不写状态文件。

调研按单个功能停止：找到足以判断行为、可复用实现、差异及验收的证据即可；GitHub 不足再扩大搜索。采用限定搜索和相关函数读取，工具输出仅保留关键证据。新证据才重开旧结论。

## 完成条件

已批准范围实现完成；适当检查和场景验收有证据；交互与实际功能一致；未解决问题清楚列出；回退与未验证边界明确。没有实际证据就不能宣称“完全一致”“已上线”或“所有错误已覆盖”。
