# 使用示例

## 新功能

用户：`$full-stack-product-manager 我想做文件上传，优先参考 GitHub 对应功能，先别写代码。`

预期：核实已有实现 → 拆分功能 → 搜索对应功能与复用条件 → 给出需求和验收 → 按需给交互/功能方案和图 → 等确认。

## 隔离交互展示

用户：`参考这个竞品的筛选功能，做一个隔离、可点击的展示，方便我对照。`

预期：观察对应竞品行为与现有组件 → 提交展示方案、交互图、隔离/模拟边界 → 等确认 → 实现展示 → 给对照步骤；不会顺带重做整个产品。

## 修复 bug

用户：`上传超时后列表显示成功，帮我修一下。`

预期：只读复现与定位 → 修复方案及红色错误/橙色恢复路径 → 等确认 → 修复 → 验证；不会直接写 catch 或把空结果当成功。

## 实施时发现新 bug

用户已确认方案 v1；验证发现权限失效后仍能提交。

预期：记录新问题，提交修复方案，暂停相关写入等待确认；原方案批准不自动覆盖新修复。

## 明确批准

用户：`确认 v2，按这个方案实现。`

预期：核实 v2 与批准范围后进入实现；不重复要求批准既定步骤。发布/push 仍需已有明确授权。

## 只读解释

用户：`解释一下这段代码，别改。`

预期：只读回答，状态写代码无；不强制展开竞品报告、不创建方案文件。
